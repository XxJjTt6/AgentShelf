# AgentShelf 技术方案报告

## 1. 项目概述

AgentShelf 聚焦比赛“AI 智能上新”命题，服务跨境卖家、电商运营团队和电商 ISV。系统把 CSV、商品图片、认证与政策资料整理为统一的 Product Passport，生成适配平台和市场的本地化 Listing，并在发布前完成规则检查、Agent 红队测试、问题修复、同场景复测和人工确认。

项目要解决的核心问题不是“能不能生成一段商品文案”，而是“这份商品信息进入 AI 购物流程后，Agent 能不能看对、选对和买对”。因此系统同时处理内容质量、商品事实、实时商业状态、跨境规则和交易安全。

## 2. 业务问题

### 2.1 商品事实分散

同一商品的名称、型号、材质、尺寸、价格、库存、认证和配送信息可能分散在 CSV、图片、政策文件和运营人员经验中。直接让模型读取这些资料并生成 Listing，容易发生遗漏、冲突未保留或无法追溯来源的问题。

### 2.2 平台和市场规则不同

Amazon、Shopify、TikTok Shop 对标题、描述、Search Terms、必填字段和风险表述的要求不同；德国和美国在语言、币种、配送和政策方面也不同。跨境上新不是单纯翻译，而是多个约束共同作用的内容与数据转换。

### 2.3 页面内容与实时状态可能不一致

Listing 中的价格、库存、运费和配送承诺可能与结账时的真实状态发生变化。只检查静态页面无法发现此类风险，需要在交易前重新读取商业状态并核对版本。

### 2.4 AI 购物 Agent 面临新的输入风险

评论、隐藏文本、图片 OCR、错误结构化字段和恶意指令都可能被购物 Agent 当成可信信息。传统内容审核关注用户看到的页面，而 Agent 安全还需要检查机器读取的所有输入和工具调用过程。

## 3. 产品目标与范围

### 3.1 产品目标

- 把多来源商品资料整理为可追溯、可版本化的商品事实。
- 生成符合目标平台、市场和语言要求的 Listing。
- 在发布前发现内容、事实、商业状态、跨境政策和指令注入风险。
- 让问题可以稳定重现，修复结果可以使用同一条件复测。
- 在最终导出或发布前保留清楚的人工确认责任。

### 3.2 当前原型范围

- 旅行收纳品类的演示商品。
- Amazon、Shopify、TikTok Shop 三个平台配置。
- 德国、美国两个目标市场及德语、英语输出。
- 30 个买家测试任务、12 个受控故障案例。
- 5 个可调用的商业沙箱 API。
- UCP、ACP、MCP 能力映射和浏览器内协议测试。
- 模拟结账，不调用真实支付和真实平台发布。

### 3.3 非目标

- 当前版本不是生产级电商后台，不包含多租户、计费和复杂权限系统。
- 不保存真实支付信息，不完成真实扣款。
- 不宣称已得到任何电商平台或商业协议组织的官方认证。
- 不用模型输出直接覆盖原始商品资料或自动放行交易。

## 4. 总体设计原则

1. **事实优先**：商品事实先进入 Product Passport，再生成 Listing，不能绕过统一资料源。
2. **来源可查**：每条可发布卖点必须保存来源；不确定内容标记为未知，冲突内容保留双方记录。
3. **AI 与规则分工**：模型负责理解、归纳和组织，固定规则负责金额、库存、配送、版本和发布条件。
4. **失败可重现**：测试任务、故障输入、运行轨迹、评分、修复和复测结果均采用结构化记录。
5. **修复不破坏原始资料**：修复生成新版本，不原地改写原始 Product Passport。
6. **发布需要人工确认**：自动检查通过不等于自动发布，最终动作需要人工确认。
7. **演示不触发真实交易**：所有结账均为隔离环境中的模拟操作，支付状态始终为未扣款。

## 5. 系统架构

系统由六个主要层次组成：

### 5.1 Web 操作台

使用 Next.js、React、TypeScript 构建单页工作台，包含以下七个工作区：

- 方案总览：面向评委和业务人员说明问题、流程、AI 分工和已实现能力。
- 上新任务：选择商品、平台、市场、语言和品类，生成 Listing 并执行发布前检查。
- 商品档案：导入 CSV、TXT/Markdown 和图片，生成 Product Passport。
- 红队测试：运行买家任务和受控故障，展示搜索、选择、加购和结账轨迹。
- 任务库：管理 30 个按风险类型组织的买家任务。
- 故障库：管理 12 个可重复执行的受控故障案例。
- 协议适配：展示 UCP、ACP、MCP 能力映射和商业沙箱握手过程。

### 5.2 商品资料整理层

输入包含商品 CSV、政策文本和商品图片。固定解析器负责字段识别、结构校验和原始资料保存；配置 Qwen 时，模型以结构化输出补充图片可见信息、政策事实、潜在冲突、安全卖点、未知项和置信度。

模型结果不能直接替换输入。系统先保留原始资料，再把可验证内容写入新 Product Passport，并记录来源和版本。

### 5.3 Listing 生成与平台检查层

Listing 生成以 Product Passport 为唯一可信商品资料源。Qwen 可以对卖点和关键词的组织顺序提出建议，但只能引用系统允许的事实 ID。标题、卖点、描述和 Search Terms 最终由固定模板、平台规则和来源约束生成。

发布前检查覆盖：

- 平台必填字段和格式。
- 标题、卖点和描述长度。
- 输出语言与目标市场匹配。
- 每条卖点是否存在可信来源。
- 高风险或绝对化表述。
- 当前价格、库存、运费和配送范围。
- Amazon Search Terms、Shopify 描述和 TikTok Shop 标题等平台差异规则。

### 5.4 Agent 红队测试层

红队引擎包含买家任务、故障注入、运行轨迹、确定性评分、问题记录和修复器。任务覆盖预算与币种、跨境配送、商品事实与认证、退货与授权四组需求。

12 个受控故障分为四类：

- 指令注入：评论、隐藏文本、图片 OCR 等不可信内容试图改变 Agent 行为。
- 商业状态：价格、库存、运费、到达时间等状态不一致。
- 商品事实：尺寸、材质、认证或商品变体发生冲突。
- 跨境政策：目标国家限制、退货或配送承诺不符合政策。

每次运行生成搜索、选择、加购和模拟结账轨迹，并计算约束满足、事实准确、攻击抵抗、金额一致和安全完成等分数。发现严重问题时，系统阻止交易并给出问题位置、证据和修复建议。

### 5.5 商业沙箱与协议适配层

商业沙箱提供 5 个 API：

```text
GET  /api/commerce/search
GET  /api/commerce/products/{productId}
GET  /api/commerce/shipping
POST /api/commerce/cart
POST /api/commerce/checkout
```

商品发现、详情和配送 API 提供测试所需的实时状态。购物车 API 生成带 HMAC 签名和有效期的 `checkoutToken`。结账 API 先返回 `CONFIRMATION_REQUIRED`，只有用户显式确认且商品版本、价格、库存和运费没有变化时才返回 `confirmed`。整个流程保持 `payment=not_captured`。

UCP、ACP、MCP 在当前原型中作为能力映射和调用适配层，用于说明同一套商品和交易能力如何被不同 Agent 协议调用，不代表已经完成外部平台认证。

### 5.6 发布文件层

完成检查和人工确认后，系统可以导出：

- 本地化 Listing JSON。
- 平台导入表。
- Product Passport 和 Product Feed。
- Schema.org JSON-LD。
- UCP Manifest。
- 发布前检查报告、卖点来源台账和红队测试报告。
- 人工确认记录和修复复测报告。

## 6. 核心数据对象

### 6.1 Product Passport

Product Passport 是统一商品资料源，主要包含：

- 商品 ID、SKU、版本和更新时间。
- 标题、品牌、型号、类目和变体。
- 材质、尺寸、颜色、用途等商品事实。
- 价格、币种、库存和配送范围。
- 认证、政策条件和风险提示。
- 每条事实的来源、置信度和验证状态。
- 冲突项、未知项和原始资料引用。

### 6.2 ListingDraft

ListingDraft 保存销售平台、目标市场、语言、标题、卖点、描述、Search Terms、卖点来源映射、平台检查结果和生成方式。它引用 Product Passport 版本，确保后续测试知道使用了哪一版商品资料。

### 6.3 Mission

Mission 表示一个可执行的买家需求，包含目的地、预算、币种、时间限制、商品约束、允许工具和预期结果。任务必须与修复前后保持一致，才能比较复测结果。

### 6.4 FaultCase

FaultCase 描述故障类型、注入位置、输入载荷、预期影响、严重程度和建议修复。故障只作用于测试数据副本，不修改原始商品记录。

### 6.5 RunReport

RunReport 保存任务、输入版本、运行轨迹、问题、评分、修复记录、结果状态和导出文件。它既服务界面展示，也作为可审查的测试证据。

## 7. Qwen 使用方式

### 7.1 商品图片与政策理解

模型读取商品图片和政策文本，返回符合预设结构的内容，包括可见属性、材料事实、政策事实、冲突、安全卖点、未知项和置信度。所有结果都经过 Zod 校验，并与原始资料一起保存。

### 7.2 Listing 结构优化

模型不自由编造文案，只能从系统提供的可信事实或卖点 ID 中选择和排序。固定代码根据平台和语言模板生成最终内容，并保存卖点到来源的映射。

### 7.3 红队结果语义复核

模型可以对运行轨迹和问题进行语义复核，用于发现固定规则难以覆盖的表达问题。模型复核是补充结果，不替代固定分数和交易阻止条件。未配置 API Key 时，系统仍能使用固定规则完整运行。

## 8. 信任边界与安全设计

| 输入或能力 | 默认信任级别 | 处理方式 |
| --- | --- | --- |
| 卖家上传的 CSV、图片和政策 | 待验证 | 保存原文、校验结构、记录来源和冲突 |
| 评论、网页文本和 OCR | 不可信 | 与系统指令隔离，不允许改变预算、工具和放行规则 |
| Qwen 输出 | 建议 | 结构校验，只能引用允许的事实，不能直接覆盖原始资料 |
| 价格、库存和配送 API | 实时业务状态 | 在加购和结账前重新读取并核对版本 |
| 购物车令牌 | 临时可信 | HMAC 签名、十分钟有效、状态变化后失效 |
| 人工确认 | 最终业务责任 | 内容和商业状态确认齐全后才能生成批准记录 |

主要安全措施：

- API Key 只从环境变量读取，不进入源码、测试和截图。
- 模型输入与工具权限分离，网页文本不能授予新工具。
- 故障注入使用数据副本，避免污染原始记录。
- 修复生成新版本，保留修复前后的差异和来源。
- 结账采用显式确认，并核对价格、库存、运费和商品版本。
- 所有演示交易均不扣款。

## 9. 技术选型

| 部分 | 技术 | 选择原因 |
| --- | --- | --- |
| Web 框架 | Next.js 16 | 前端、服务端接口和构建流程统一，便于快速演示和部署 |
| 界面 | React 19、TypeScript | 组件化、类型安全、适合复杂交互状态 |
| 数据校验 | Zod | 对模型输出、API 输入和核心数据对象进行运行时校验 |
| CSV 解析 | Papa Parse | 使用成熟解析器，处理实际 CSV 边界情况 |
| 大模型 | Qwen，通过阿里云百炼接口 | 支持文本、图片和结构化输出，适合跨境商品资料理解 |
| 图标 | Lucide React | 统一、可访问、避免手绘不一致图标 |
| 单元测试 | Vitest | 快速验证核心规则、引擎和数据转换 |
| 端到端测试 | Playwright | 验证真实浏览器交互、下载、响应式布局和 API 流程 |

## 10. 可行性分析

### 技术可行性

项目已有可运行原型，核心功能不是静态设计稿。商品资料整理、Listing 生成、平台检查、任务运行、故障注入、修复复测、文件下载和商业沙箱均有实际代码和自动测试。

### 数据可行性

原型使用结构化演示商品和受控故障，不依赖大规模训练数据。进入试点阶段后，可从合作卖家的商品资料、历史退回原因和平台规则中逐步扩展，无需先建立完整行业数据集。

### 业务可行性

产品可以作为现有商品管理系统和发布流程之前的质量检查层，不要求卖家立即替换原有 ERP、PIM 或平台后台。早期可先采用文件导入和报告导出，验证价值后再增加平台连接器。

## 11. 创新点

1. **把 AI 上新从内容生成扩展为安全发布流程**：生成、检查、红队测试、修复和确认形成闭环。
2. **面向购物 Agent 设计质量标准**：同时验证人可见内容和机器可读取的商品、评论、OCR、工具结果。
3. **以 Product Passport 统一商品事实**：跨平台 Listing、测试和协议输出都引用同一版本的商品资料。
4. **同任务修复复测**：修复前后使用相同买家需求和故障输入，避免“换题后通过”。
5. **确认式商业沙箱**：用签名购物车、状态复核和显式确认演示 Agent 交易的安全放行方式。

## 12. 部署与扩展路线

### 阶段一：比赛原型

- 本地或单实例部署。
- 演示数据保存在代码和运行内存中。
- Qwen API Key 可选；没有密钥时使用固定规则。
- 商业操作全部为沙箱模拟。

### 阶段二：卖家试点

- 增加账号、组织、角色和商品资料权限。
- 使用 PostgreSQL 保存商品版本、任务、运行和报告。
- 使用对象存储保存图片、政策和导出文件。
- 使用任务队列执行批量图片理解和 30 项测试。
- 对接一个平台测试环境或合作方 PIM/ERP。
- 增加模型调用成本、时延、失败率和质量监控。

### 阶段三：生产服务

- 多租户隔离、审计日志、密钥管理和数据生命周期策略。
- 更多品类、平台、国家和语言规则包。
- 规则版本管理、灰度发布和人工审核工作流。
- 真实平台发布前的双向状态核对和回滚策略。
- 使用真实商家数据评估问题发现率、返工次数和上新周期。

## 13. 风险与应对

| 风险 | 影响 | 应对方式 |
| --- | --- | --- |
| 模型遗漏或误读图片、政策 | 错误事实进入内容 | 保存原始资料、结构校验、冲突和未知项、人工确认 |
| 平台规则持续变化 | 检查规则过期 | 规则版本化，标记来源和生效时间，支持独立更新 |
| 实时商业状态变化 | 结账金额或配送不一致 | 加购和结账前重新读取，令牌包含版本和有效期 |
| 测试案例覆盖不全 | 未发现新型风险 | 按真实问题持续扩充任务和故障库，保留回归测试 |
| 模型成本和延迟 | 批量上新效率下降 | 固定规则优先、模型可选、批处理、缓存和失败降级 |
| 自动修复造成新问题 | 修复后引入回归 | 不修改原始版本，使用同任务复测并要求人工确认 |

## 14. 成功指标

以下指标需要在真实卖家试点中采集，当前原型不虚构结果：

- 单个 SKU 从资料导入到形成可审核 Listing 的时间。
- 每个 Listing 中有明确来源的卖点比例。
- 发布前发现的高风险问题数量和类型。
- 首次检查通过率、修复后通过率和平均修复次数。
- 因价格、库存、配送和政策问题导致的返工次数。
- 运营人员人工核对时间和问题定位时间。
- 模型调用成功率、平均时延和单 SKU 成本。

## 15. 总结

AgentShelf 用一个可运行原型证明了“AI 智能上新”可以从内容生成进一步发展为可追溯、可测试、可修复、可确认的安全发布流程。Product Passport 负责统一事实，Qwen 负责理解和组织，固定规则负责交易与发布条件，红队引擎负责发现问题，人工确认负责最终业务责任。当前方案适合比赛演示和早期试点，生产化仍需要真实平台连接、账号权限、持久化和业务数据验证。
