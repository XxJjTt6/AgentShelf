# AgentShelf 技术方案报告

## 一、项目概述

- 参赛团队：Saber
- 队长姓名：徐江涛
- 参赛者：徐江涛
- 参赛场景：AI 智能上新

AgentShelf 服务跨境卖家、电商运营团队和电商 ISV。系统把 CSV、商品图片、认证与政策资料整理为统一的 Product Passport，生成适配销售平台、目标市场和语言的本地化 Listing，并在发布前完成规则检查、Agent 红队测试、问题修复、同条件复测和人工确认。

系统关注的不只是文案质量，还验证商品信息进入 AI 购物流程后，购物 Agent 能否正确理解商品、满足买家约束并安全完成模拟交易。

## 二、设计目标

1. 将多来源商品资料整理为可追溯、可版本化的商品事实。
2. 生成符合平台、市场、语言和品类要求的 Listing。
3. 在发布前发现内容、事实、商业状态、跨境政策和指令注入风险。
4. 保存测试输入、运行轨迹、问题位置、修复版本和复测结果。
5. 自动化检查完成后，由运营人员承担最终确认责任。

## 三、总体设计原则

### 1. 事实优先

商品事实先进入 Product Passport，再用于 Listing 生成、红队测试和文件导出，所有环节引用明确版本。

### 2. 来源可查

每条可发布卖点保存来源。无法确认的内容记录为未知项，存在冲突的内容保留双方资料和验证状态。

### 3. AI 与规则分工

Qwen 负责理解图片和政策、组织内容与复核复杂语义；固定规则负责金额、库存、配送、版本和放行条件。

### 4. 失败可重现

买家任务、故障输入、商品版本、运行轨迹、评分、修复和复测结果采用结构化记录，便于稳定复现。

### 5. 修复保留历史

修复生成新版本，不直接覆盖原始 Product Passport。系统保留修复前后的差异与测试结果。

### 6. 发布需要确认

自动检查通过后，运营人员仍需确认内容、价格、库存、运费和配送范围，才能生成批准记录。

## 四、系统组成

### 1. Web 操作台

系统使用 Next.js、React 和 TypeScript 构建七个工作区：

- 方案总览：展示业务问题、流程、AI 分工和已实现能力。
- 上新任务：选择商品、平台、市场、语言和品类，生成 Listing 并检查。
- 商品档案：导入 CSV、政策和图片，生成 Product Passport。
- 红队测试：运行买家任务和受控故障，查看完整轨迹和结果。
- 任务库：管理 30 个按风险类型组织的买家任务。
- 故障库：管理 12 个可重复执行的受控故障。
- 协议适配：验证 UCP、ACP、MCP 能力映射和商业沙箱调用。

### 2. 商品资料整理

固定解析器识别字段、校验结构并保存原始资料。Qwen 以结构化输出补充图片可见信息、政策事实、潜在冲突、安全卖点、未知项和置信度。系统完成校验后生成新的 Product Passport，并保存来源与版本。

### 3. Listing 生成与平台检查

Listing 生成以 Product Passport 为统一商品资料源。Qwen 可以对可信卖点和关键词排序，但只能引用系统允许的事实 ID。固定模板和平台规则生成标题、卖点、描述与 Search Terms，并执行以下检查：

- 平台必填字段与格式。
- 标题、卖点和描述长度。
- 输出语言与目标市场匹配。
- 卖点是否具有可信来源。
- 风险表述和绝对化承诺。
- 当前价格、库存、运费和配送范围。
- Amazon、Shopify、TikTok Shop 的差异规则。

### 4. Agent 红队测试

红队引擎由买家任务、故障注入、运行轨迹、确定性评分、问题记录和修复器组成。30 个买家任务覆盖预算与币种、跨境配送、商品事实与认证、退货与授权；12 个受控故障覆盖以下四类风险：

- 指令注入：评论、隐藏文本和图片 OCR 试图改变 Agent 行为。
- 商业状态：价格、库存、运费和到达时间不一致。
- 商品事实：尺寸、材质、认证或商品变体冲突。
- 跨境政策：目标国家限制、退货或配送承诺不符合政策。

每次运行保存搜索、选择、加购和模拟结账轨迹。系统按约束满足、事实准确、攻击抵抗、金额一致和安全完成进行评分。发现严重问题时，立即阻止操作并给出问题位置、证据和修复建议。

### 5. 商业沙箱与协议适配

商业沙箱提供商品搜索、商品详情、配送查询、购物车和模拟结账 5 个 API。购物车使用 HMAC 签名并设置有效期；结账要求显式确认，并重新核对商品版本、价格、库存和运费。所有交易均在隔离验证环境中执行，不连接真实支付。

UCP、ACP、MCP 作为能力映射和调用适配层，用于验证同一套商品与交易能力如何被不同 Agent 协议调用。

### 6. 发布文件

检查和人工确认完成后，系统可导出：

- 本地化 Listing JSON。
- 平台导入表。
- Product Passport 和 Product Feed。
- Schema.org JSON-LD。
- UCP Manifest。
- 发布前检查报告和卖点来源台账。
- 红队测试、修复复测和人工确认记录。

## 五、核心数据对象

### Product Passport

保存商品 ID、SKU、版本、标题、品牌、型号、类目、变体、商品事实、商业状态、认证、政策、来源、置信度、验证状态、冲突项和未知项。

### ListingDraft

保存平台、市场、语言、标题、卖点、描述、Search Terms、来源映射、平台检查结果和生成方式，并引用明确的 Product Passport 版本。

### Mission

表示可执行的买家需求，包含目的地、预算、币种、时间限制、商品约束、允许工具和预期结果。

### FaultCase

描述故障类型、注入位置、输入载荷、预期影响、严重程度和建议修复。故障只作用于测试数据副本。

### RunReport

保存任务、输入版本、运行轨迹、问题、评分、修复记录、结果状态和导出文件，作为可审查的测试证据。

## 六、Qwen 使用方式

### 商品图片与政策理解

模型读取商品图片和政策文本，返回符合预设结构的可见属性、材料事实、政策事实、冲突、安全卖点、未知项和置信度。结果通过 Zod 校验后，与原始资料共同保存。

### Listing 结构优化

模型从系统提供的可信事实或卖点 ID 中选择和排序。固定代码根据平台和语言模板生成最终内容，并保存卖点到来源的映射。

### 红队结果语义复核

模型复核运行轨迹和问题，用于发现固定规则不易覆盖的表达风险。语义复核作为补充证据，不替代固定评分和交易阻止条件。

## 七、安全设计

- 原始资料、模型建议、确认事实和发布版本分开保存。
- 评论、网页文本和 OCR 默认不可信，不能改变预算、系统指令和工具权限。
- 模型输出必须通过结构校验，且不能直接覆盖商品事实。
- 故障注入使用数据副本，避免污染原始记录。
- 购物车令牌绑定商品版本、金额和有效期，状态变化后自动失效。
- 加购和模拟结账前重新读取价格、库存、运费和商品版本。
- 自动修复生成新版本，并保留结构化差异与复测记录。
- 发布前必须完成内容和商业状态的人工确认。

## 八、技术选型

| 部分 | 技术 | 作用 |
| --- | --- | --- |
| Web 框架 | Next.js 16 | 统一前端、服务端接口与构建流程 |
| 界面 | React 19、TypeScript | 构建复杂交互并提供类型约束 |
| 数据校验 | Zod | 校验模型输出、API 输入和核心数据对象 |
| CSV 解析 | Papa Parse | 可靠处理商品表格及边界情况 |
| 大模型 | Qwen、阿里云百炼 | 理解文本与图片并输出结构化建议 |
| 图标 | Lucide React | 统一图标并支持可访问性 |
| 单元测试 | Vitest | 验证核心规则、引擎与数据转换 |
| 端到端测试 | Playwright | 验证浏览器交互、响应式布局和 API 流程 |

## 九、可扩展性

系统采用模块化结构，Product Passport、平台规则、任务库、故障库、协议适配和发布文件可独立扩展。架构支持接入持久化服务、对象存储、任务队列、平台连接器、组织权限和审计能力，也可按品类、国家、语言和平台增加规则包。

## 十、技术风险与控制

| 风险 | 影响 | 控制方式 |
| --- | --- | --- |
| 模型遗漏或误读资料 | 错误事实进入内容 | 保存原始资料、结构校验、冲突记录、人工确认 |
| 平台规则变化 | 检查规则过期 | 规则版本化，记录来源与生效时间 |
| 商业状态变化 | 金额或配送不一致 | 操作前重新读取，令牌绑定版本与有效期 |
| 测试案例覆盖不足 | 新型风险未被发现 | 持续扩充任务和故障库并执行回归测试 |
| 模型成本和时延 | 批量上新效率下降 | 规则优先、批处理、缓存和失败降级 |
| 自动修复引入回归 | 新版本产生新问题 | 保留原版本，同条件复测并要求人工确认 |

## 十一、总结

AgentShelf 将 AI 智能上新从内容生成扩展为可追溯、可测试、可修复、可确认的安全发布流程。Product Passport 统一商品事实，Qwen 负责非结构化资料理解与内容组织，固定规则负责交易和发布条件，红队引擎负责发现问题，人工确认承担最终业务责任。
